# 术语表：双世界与内核边界（团队必读，术语权威）

> 定位：全项目的**术语统一权威**——任何文档/图示/讨论使用本表口径。
> 一句话锚点：**"GameWorld 属于 Runtime World 侧（Game 即 Runtime，不加前缀）"；
> "Gateway 对接的是 Godot Core，经其 Server API（Godot Core 是概念、Server API 是实现细节）"。**
> 关联：`性能路径与跨语言边界.md`、`O5-GameWorldHost与ServerPorts.md`、`Node能力去向与复用边界.md`。

## 1. 术语表（钉死）

| 术语 | 定义 | 分层 | 用法 |
|---|---|---|---|
| **Design World**（设计世界） | 心智模型层：回答"世界应该是什么样"——静态数据、声明式、可保存 | 心智模型层 | 概念讨论、文档标题 |
| **Runtime World**（运行世界） | 心智模型层：回答"现在正在发生什么"——动态状态、模拟 | 心智模型层 | 概念讨论、文档标题 |
| **EditorSession / 文档模型** | Design World 的实现：编辑 .bscene/.bprefab 数据（GameWorldSnapshot） | 实现层 | 代码、O7 文档 |
| **GameWorld** | Runtime World 的具体实现（代码类）——**Game 已指 Runtime，不加前缀** | 实现层 | 代码、实现文档 |
| **Gateway** | Runtime World 与 Godot Core 的唯一对接点（唯一跨语言缝） | 实现层 | 代码、O5/O6 文档 |
| **Godot Core** | 我们保留并使用的 **Godot C++ 内核子集**（概念：渲染/物理/资源/平台管线） | 概念层 | 图示、架构总览 |
| **Server API** | Godot Core 内我们实际对接的具体 API 面（RenderingServer/PhysicsServer/Nav/Audio…）——**Godot Core 是概念，Server API 是实现细节** | 实现细节 | 技术细节描述 |

## 2. 分层图（唯一口径）

```text
┌─────────────────────────────────────────┐
│ Design World（设计世界）      [心智模型层]  │
│   └─ EditorSession（文档模型）  [实现层]    │
│        │ .bscene 保存/载入（Design ↔ 文件）│
│        ▼                                │
│ Runtime World（运行世界）      [心智模型层]  │
│   └─ GameWorld（语义核心）      [实现层]    │
│        │ Gateway（唯一对接点）             │
│        ▼                                │
│ Godot Core（C++ 内核，保留子集）  [概念层]   │
│   └─ Server API（RenderingServer/…）     │ ← 实际触摸的入口（实现机制）
└─────────────────────────────────────────┘
```

## 3. 用法细则（防混用）

- **"GameWorld" 永不写 "RuntimeGameWorld"**：Game 已隐含 Runtime 侧（如同 Unity 的 GameScene 不用叫 RuntimeScene）。若要强调与 Design 对照，说"GameWorld（Runtime World 侧）"。
- **"Godot Core" 是概念**（我们保留的 C++ 内核子集——不是整个 Godot）；**"Server API" 是实现细节**（Core 内我们触碰的具体入口）。图示统一写 **Godot Core**，技术细节用 Server API。
- **"Gateway" 是唯一术语**：不再叫 Backend/Blend/Adapter（历史名勿恢复；性能文档等旧表述已统一）。
- **"编辑器" 动词化**：做编辑的叫 EditorSession（Design 侧）；"3D view 显示"= 预演（Design 文档 → 临时 Runtime 世界 → Gateway → Server API 投影），不是"把编辑器当运行时"。

## 4. 一句话对照（面试/汇报口径）

> 我们的引擎 = **Design World（编辑 .bscene）→ Runtime World（GameWorld 纯 C# 语义）→ Godot Core（经 Gateway + Server API 触碰保留的 C++ 内核子集）**。

## 5. 编辑器三层构成（权威界定，2026-08-23 用户裁定）

**编辑器 = 数据核心 + UI 壳 + 渲染能力**——三层各答"用不用原生 Godot 编辑器"：

```text
┌──────────────────────────────────────────────┐
│ 编辑器                                          │
│                                              │
│ ① 数据核心（纯 .NET 自建，已有：src/libs/editor） │
│    EditorSession / GameWorldSnapshot          │
│    = 编辑 Object+Component / undo / .bscene   │
│    → 与 Godot 编辑器零关系（数据链是两套）        │
│                                              │
│ ② UI 壳（dock/面板/3D 交互）                   │
│    ← 原生 SceneTreeDock/Node3DEditor 以 Node  │
│      为中心，不能直接用（§7：不能只改文字）       │
│    → 过渡：改造 Node3DEditor 接受 ObjectSelection│
│      （§7.3：ObjectSelection → ComponentGizmoAdapter│
│       → gateway gizmo）；终局：Avalonia 自建 UI  │
│      （D5 终极目标）                           │
│                                              │
│ ③ 渲染能力（3D view 底层）                     │
│    ← 复用 Godot Core 的 RenderingServer        │
│      （这是"内核能力"不是"Node 编辑器"，照用）    │
└──────────────────────────────────────────────┘
```

- **原生 Godot 编辑器作为"Node 为中心的编辑器"整体不用**：其数据链（Node → SceneTreeDock → Inspector 读 Node 属性 → PackedScene 存 Node 树）与我们的 GameObject+Component+GameWorldSnapshot 两套，接不上；
- **RenderingServer 渲染能力作为 Godot Core 复用**（用编辑器 ≠ 用渲染内核；后者一直在用）；
- **src/libs/editor = 数据核心**（已建、headless 可测）；**UI 壳是 O7.5+ 的事**（过渡走 §7.3 改造 Node3DEditor，终局 D5 Avalonia）。

### 5.1 Avalonia 编辑器壳具体方案（2026-08-23 落地，参考 Native interop 调研）

**终局编辑器 = `Editor.exe`（Avalonia 壳）嵌 Godot 渲染 Viewport**，两种集成路线：

```text
方案 A（第一版，推荐）：Native Child View
  Avalonia Window
    ├─ Hierarchy / Inspector / Assets / Console   ← C# UI
    └─ ViewportHost（Avalonia NativeControlHost）
         └─ Native View（Windows: HWND / macOS: NSView / Linux: X11）
              └─ Godot Renderer 自建 swapchain 渲染（零 GPU 拷贝）

方案 B（不做第一版）：Godot RenderTexture → 共享 GPU 纹理 → Avalonia Composition
  需解决 Vulkan/D3D texture sharing + fence + lifetime（跨平台各做一遍），复杂度高
```

- **Avalonia 不参与 3D 渲染**——`NativeControlHost` 只嵌原生窗口句柄；Godot 自己渲染，性能/延迟最优；
- **airspace 限制**：native 子视图上无法叠加 Avalonia 控件（z-order/clipping 边界）——**Gizmo/Grid/Selection/Overlay 全部由 Godot Renderer 画**（经 Gateway → RenderingServer/RID），Avalonia 只画 Viewport 外围 UI——这与我们"3D view = Gateway 投影"方向一致；
- **编辑器共享状态走 Editor Model 而非控件同步**：Hierarchy 点击 → SelectionService → Inspector 显示 + Native Viewport 高亮同一对象（`EditorSession`/`GameWorldSnapshot` 即共享数据库，与我们 O7 数据核心一致）；
- C# 侧通过**薄 Native API**（`editor_create_viewport(parent_handle)` / `resize` / `render` / `mouse_move`…）驱动——是 §5.2 Native Interop Layer 规范的具体实例。

## 6. Native Interop Layer（统一 Native 边界规范，2026-08-23 落地）

> 核心认知（架构分层）：**Godot Core = 整个 All-in C# 架构中最大、最复杂的一个 Native Module。**
> 它不是"第二套世界"，而是 C# Host 下一个 Native Backend——未来所有 C++ 性能模块（mesh/pathfinding/image/audio/GPU backend）
> 走**同一套**边界规范，`Gateway`（Godot 专用）成为该规范下第一个实例。

```text
Managed / C#（唯一业务 API owner）
  ─────────────────────────────
  Engine.Native                ← 统一 Native 互操作层
    ├── Godot   （Gateway，现有）
    ├── Mesh    （未来 C++ 模块）
    ├── Image   （未来）
    ├── Audio   （未来）
    └── ...     （未来）
        ↓ 统一边界
  C ABI + LibraryImport        ← Windows dll / macOS dylib / Linux so
  Handle + POD                 ← 不暴露 C++ 对象；SafeHandle 管理生存期
  Span<T> / pointer + count    ← 批量数据
  Batch API                    ← 一次 crossing 完成大量工作
  ─────────────────────────────
Native / C++（implementation detail）
```

**统一边界铁律**：
- **C# 定义业务 API**；native 模块只是 implementation detail（可替换实现：C++/Rust/C# 版本互换）；
- **C ABI + `LibraryImport`**（source-generated interop，比 DllImport 更可控、NativeAOT 友好）；
- **Handle 模式**：跨边界只传 `void*` handle / POD，不传 C++ 对象；`SafeHandle` 管理生命周期；
- **批量**：一次调用传 `(ptr, count)` 完成大批工作（如 `scene.UpdateTransforms(TransformUpdate[], count)`）；
- **回调**：高频反调走"批量处理→返回结果"，不建议逐元素 callback 回 C#。

**热路径规则集（性能由架构保证）**：
```text
热路径禁止 string / Variant / 逐对象 getter / 集合分配
热路径必须 batch；大数据必须 pointer + count；跨边界只传 Handle/POD
```
——把"30,000 次细粒度 crossing"变成"1 次批量 crossing"，是数量级差异；`GatewayCommand` 可演进为批量命令。

**与既有路线的对应**：
- `Gateway`（唯一对接点）= 本规范下 Godot backend 的实例（现有 IGateway 接口族）；
- 未来 C++ 性能模块（O8+ 遇热点时）按本规范加入 `Engine.Native`，不另设互操作形态；
- 编辑器 Viewport 驱动（§5.1 薄 Native API）同属本规范。
