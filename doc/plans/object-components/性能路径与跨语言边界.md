# 性能路径与跨语言边界（团队必读）

> 定位：O6 完成后的**性能认知文档**——帮助团队理解"我们的 C# 与 Godot C++ 的性能关系"、
> 为什么 GDScript 调节点的优势在我们架构里不存在、以及未来想加速 gateway 时的升级方案。
> 一句话结论：**游戏世界 = 纯 C# 自足（零跨语言）；Godot C++ 只是画师和物理引擎（低频 Gateway 伺候）；GDScript 的性能优势路径我们压根没有对应场景。**
> 关联文档：`Node能力去向与复用边界.md`（Node 能力去哪了）、`O5-GameWorldHost与ServerPorts.md`、`O6-GameWorldGateway与垂直切片.md`。

## 1. Godot 语言性能真相（先掰正几个常见误解）

| 误解 | 事实 |
|---|---|
| GDScript 是"直接转 C++"，性能强 | **不是**。GDScript 编译到**字节码**，在 GDScript 虚拟机上解释执行（`modules/gdscript/gdscript_vm.cpp`）。它比 C# 慢（纯逻辑差 4-10 倍量级）。"一等公民"指**生态地位**（易写/官方示例/文档），不是性能 |
| GDScript 调引擎方法比 C# 快 | **部分对**。脚本调**引擎方法**时：GDScript 在虚拟机内直调 C++ 方法；C# 要走 GodotSharp 绑定的 marshaling（Variant/StringName/参数编组），编组开销吃掉了 JIT 优势——**所以在"调引擎方法"这条路上两者接近**。C# 的真实优势只在**纯托管逻辑**（循环/算法/数据结构） |
| GodotSharp 是什么 | Godot 官方 C# 支持 = `modules/mono/glue` 从引擎源码生成的**绑定层**（C# ↔ C++ 翻译库）。官方 C# 唯一路径 |

## 2. 我们的性能路径：把跨语言缝压到最低

```text
┌──────────────────────────────────────┐
│  C# 内部（纯 .NET，零跨语言）          │
│   GameWorld / GameObject / Components │  ← 游戏逻辑全在这
│   生命周期 / 层级 / 关系 / tick / 序列化│  ← 零 Godot、零 Node、零 Friflo
└──────────────┬───────────────────────┘
               │ 只有这处跨语言（Gateway 投影，低频）
               ▼
┌──────────────────────────────────────┐
│  Backend（每帧几十个命令）             │
│  RenderGateway → RenderingServer      │  ← C++ 只管画出来
└──────────────────────────────────────┘
```

| 层 | 跨语言？ | 说明 |
|---|---|---|
| Gameplay 逻辑（组件/tick/序列化/hash） | **零** | 纯 .NET 托管内存内完成，Godot C++ 一个字节没参与（O1 门禁 + O2 POC 证明） |
| Gateway 投影 | 低频（每帧数十命令） | 把 C# 语义"画"到 C++ 渲染/物理；不是热点，不需要快 |
| 宿主进程壳（GodotSola3dMainLoop） | 引导用 | 只负责进程活着 + 每帧推一把 GameWorld，是外壳不是游戏 |

**推论**：
- GDScript"调节点更快"的优势路径——**我们完全没有对应场景**——因为 Gameplay 根本不调引擎节点；
- C# "纯逻辑快"的真实优势——**我们用满了**（全部游戏逻辑都是纯托管）；
- 性能大头（渲染/物理求解）本来就在 **C++ Server 内**（RenderingServer/PhysicsServer 复用，不重写）。

### 与官方 C# 玩法的本质区别

```text
Godot 官方 C# 玩法：在 Godot 里用 C# 写脚本——每个节点交互都过绑定缝
我们的玩法：GameWorld 在 C# 自治，Godot 只当显示器/物理引擎——跨语言缝被 Backend 隔离成低频
```

## 3. 未来升级方案：薄绑定通道（fork 特权，最优候选）

**当前状态**：主流路径走 GodotSharp 通用绑定（任何方法都统一过 Variant/StringName 编组）。
**未来痛点**：若出现"每帧上万个 Transform 投影"级别的高频 backend 需求，GodotSharp 的 marshaling 税会显现。

**方案（候选 2）**：我们在引擎模块里为热点路径**专门导出直通函数**——C# 侧用 blittable struct（原样 `Transform3D`/`Vector3`，零装箱）直接 P/Invoke 进 C++，**跳过 Variant/StringName 编组**：

```text
现在（GodotSharp）：   C# → 构造 Variant → StringName 查表 → C++ 方法（通用、完整、有编组税）
薄绑定通道（fork）   ： C# → 原始 struct 指针 → C++ 导出的直通函数（无编组，近零边界开销）
```

**为什么只有我们能做**：薄通道需要改引擎源码（在 Server API 层导出 C ABI 直调函数）——这是 fork 特权，GDExtension 未来也拿不到（它只能走 ClassDB 白名单 + C ABI 接口）。

**落点**：优化只改 **backend 内部实现**，不动 GameWorld——这正是 Backend 隔离层的设计红利：
`SceneProjector` 投影逻辑（纯 C# 读组件）不变，只有 `IRenderGateway` 的 Godot 侧实现换成薄通道调用。

**触发时机**（不预先做）：
1. profiling 证明 Gateway 投影是热点（如几十万实例 Transform 更新）；
2. O8 域迁移出现高频物理/动画回传；
3. 在发生前，GodotSharp 绑定税占比可忽略，不值得提前引入复杂度。

**native AOT（候选 3，最次）**：C# AOT + 静态导出压托管启动/反射成本——适合最终发行版，开发期不必。

## 4. FAQ

- **"GDScript 调节点快，我们是不是亏了？"** 不亏。我们 Gameplay 不调节点（纯 C# 自治），那条路不存在；纯逻辑 C# 反而更快。
- **"我们要不要现在就上薄绑定通道？"** 不要。跨语言缝已是低频，绑税可忽略；等 profiling 证明热点再上（本方案已备好）。
- **"薄绑定通道是不是=GDExtension 换皮？"** 不是。GDExtension 是**外部**代码经 ClassDB 白名单进 Godot；薄通道是**引擎模块内**直接改源码导出的 C ABI——访问权完全不同（模块 ⊆ 全量头文件），且无版本兼容层开销。
