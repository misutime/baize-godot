# O3 可读格式契约草案 —— GameWorldSnapshot ↔ 文本（.bscene/.bprefab 前置规范）

> 阶段：O3 工件 2（§14.10 修订路线：O3 = GameObject C# bindings + Component Schema；O4 = `.bscene/.bprefab` 最小格式和实例化计划）。
> 本文件是 **格式权威**：O4 的 `.bscene/.bprefab` loader 与 O7 编辑器落盘都以此为准；改格式先改本文档。
> 关联契约：`O1-GameObject语义契约.md` R7（稳定全限定名）/ R22（Schema 编译委托）/ R24（未知项容错）/ R26（本文档条目）。
> 实现：`modules/gameobject/GameWorldTextSerializer.cs`（`Baize.GameObject` 命名空间）；验证：`test-projects/gameobject-core-tests/`。
> 2026-08-23 shifu 评审后修订：DFS 校验强化、头部阶段化、非有限浮点拒绝、块边界转移、严格转义与 token 系统（详见 §3.x 各条与「评审修订记录」）。

## 1. 目标与非目标

- **目标**：确定性、可读、可 diff、Git 友好的文本编码，表达一次 `GameWorldSnapshot` 的全部内容
  （对象记录 + 组件记录 + 关系记录）；`Capture→Serialize→Deserialize→Restore→Capture` hash 相等；
  同快照 Serialize 两次字节相等；`Serialize→Deserialize→Serialize` 幂等。
- **非目标**：O4 的 `.bscene`/`.bprefab` 文件格式、prefab override 记录（B3，O4）、
  编辑器 Inspector 双向编辑协议（O7）。本文档只定义「快照 ↔ 文本」这一层。

## 2. 文件名与命名

- 类：`GameWorldTextSerializer`（静态类，`Serialize(GameWorldSnapshot) → string`、`Deserialize(string) → GameWorldSnapshot`）。
- 约定：文本格式名为 `baize.object-components.v1`；扩展名草案 `.bscene`（场景）/ `.bprefab`（预置）在 O4 定文件级细节。

## 2.1 形态选型：平铺 + DFS 序号引用（2026-08-23 三次修订定稿）

对比过的主流方案全部采用「平铺 + 显式引用」：

| 方案 | 层级表达 | 块边界 | 引用 |
|---|---|---|---|
| Godot `.tscn` | `parent="NodePath"` | `[node name=...]` 头 | NodePath 名字路径 |
| Bevy BSN / `.scn.ron` | `Parent(entity)` 组件 / RON 括号 | 实体列表项 | 实体数字 id |
| Unity UnityYAML | `m_Father: {fileID: ...}` | `--- !u!1 &id` 文档头 | fileID 稳定 id |

**三次修订的结论**：
1. **首版**用缩进表达层级 → 弃用：解析依赖缩进深度、diff 噪音大、层级断裂难排查。
2. **修订一**（tscn 风格）用对象名字做引用 → 弃用：**名字是展示名不是身份**——运行时重名是
   常见场景（批量 spawn），名字唯一性会导致合法快照无法序列化；且消歧要依赖 O4 的
   `AuthoringId`，让 O3 自洽层被下一阶段卡脖子。
3. **修订二（定稿）**：**平铺 + DFS 序号引用**（Bevy/Unity 数字 id 同构）——引用一律 `#<序号>`，
   **对象名仅作人读展示标签，不参与任何引用**；对象名可重复，序列化零约束。
4. **评审修订（shifu，2026-08-23）**：DFS 序号只适合**单次快照的紧凑索引**（Restore 父子/关系端点映射、
   测试、中间表示）；不适合作为长期作者身份（prefab override、多人 Git 合并、跨场景引用）。
   O4 的 `.bscene/.bprefab` 应引入 **AuthoringId 双身份**：文件内 `object @<稳定ID> "<名字>"` + `parent = @<ID>`
   引用，loader 建立 `@ID → #DFS索引` 映射后再构造快照（见 §6.2）。本层序号契约不改。

**为什么引用不依赖名字**（核心决策）：
- 序号 = 快照索引 = DFS 序 = `ParentIndex` 来源，**三层同构**：`Deserialize` 直译即得，无名字查找表。
- 任意合法快照（含重名对象）都可序列化，O3 完全自洽，不依赖 O4。
- 名字唯一性不是身份约束；O4 如需「作者场景重命名/重排的稳定参照」，再引入 `AuthoringId`（§6.2），
  与本层序号引用正交。

**缩进无含义**：解析器忽略行首空白（纯排版），层级断裂不可能发生；新增对象只增行、不动他人行
（唯一代价：DFS 序号在插入时整体后移——这是快照自身顺序的诚实反映，与 Capture 的确定性口径一致）。

## 3. 文本格式规范（v1）

### 3.1 头部（强制，评审修订：阶段化）

```text
format = "baize.object-components.v1"
kind = "scene"
```

- **首条有效行**（第一条非空、非注释行）**必须是 `format`**，且值固定为 `baize.object-components.v1`；
  其他值 → `InvalidOperationException`（明确版本不兼容报错）。
- **第二条有效行必须依次是 `kind`**，且值必须是 `"scene"`（本文档范围）。`"prefab"` 由 O4 定义。
- **每条头部字段只能出现一次**；重复 `format`/`kind` → 报错。
- **头部必须位于任何对象/组件/属性/关系行之前**；进入正文后再次出现头部 → 报错。
- 头部后空一行；其余空行/整行 `#` 注释可出现在任意位置（含头部前），解析时忽略。

### 3.2 对象行（平铺 + 序号引用；DFS 序严格校验）

```text
object #0 "主场景"
object #1 "CubeA" parent = #0
object #2 "敌人"
object #3 "x" parent = #1
object #4 "x" parent = #1
```

- `object #<DFS序号> "<名字>"`：序号 = 快照索引 = **DFS 深度优先序**（父先子后，与 Capture 一致）。
- 名字 = **人读展示标签**：双引号包裹 UTF-8，转义同属性 string（见 3.5）；**可重复**，不参与引用。
- **父子关系 = `parent = #<父序号>`**（显式引用）：缺省 = 顶层对象。
- **DFS 序严格校验（评审修订）**：不只要求 `父序号 < 当前序号`，还需满足完整 DFS 前序——
  `Deserialize` 用**祖先栈**验证：顶层对象清空栈；非顶层对象的 parent 必须在当前开放祖先链中；
  一旦退出某子树，后续对象不得再引用该子树内节点（示例 `#0 A → #1 A-child → #2 B → #3 A-grandchild(parent=#1)`
  是**非法**序列——顶层 B 出现后不得回到 A 子树）。校验失败 → 报错（带行号）。
- **Serialize 前置 `ValidateSnapshot`（评审修订）**：Serialize 对每个对象校验
  `ParentIndex ∈ {-1} ∪ [0, i)`（父索引必须 < 自身且非自身）；**非法 ParentIndex → 直接抛错**
  （禁止静默降级为顶层，避免数据损坏）。Serialize/Deserialize 共用同一校验语义。
- 对象可带 `enabled = false` 尾注：`object #4 "x" enabled = false`（缺省 enabled = true）；
  尾注顺序任意（`parent` 与 `enabled` 可互换）。
- **缩进无含义**：解析器忽略行首空白（仅排版美观）。

### 3.3 引用与身份（为什么不用名字）

- **展示与身份分离**：对象名只是给人看的标签，`parent`/`relation` 一律用 `#<DFS序号>`。
- **无名字唯一性约束**：重名对象合法且可序列化（运行时批量 spawn 是常态）。
- **序号即身份**：`#n` 直接映射快照索引，解析零歧义、零查找；序号连续（3.2）+ DFS 前序（3.2）双重校验。
- 引用目标约束：`parent = #p` 要求 `p` 在开放祖先链中（3.2）；`relation … #s -> #t` 要求
  `0 ≤ s,t < 对象总数`。违反 → 解析报错（带行号与引用上下文）。

### 3.4 组件行与块边界（`[component]` 块头切块；状态转移严格）

```text
[component MyGame.Health]
    Max = 50
    Current = 37
[component MyGame.Buff]
    Name = "攻速"
    Amount = 1.5
```

- `[component <稳定全限定名>]`（R7）；可带 `enabled = false` 尾注：
  `[component MyGame.Health enabled = false]`（缺省 true）。**无 `disabled` 简写**。
- **块边界 = 标记行（评审修订：状态转移严格）**：属性行归属最近一个 `[component]` 块；
  块结束于下一个 `[component]` / `object` / `relation` /（非法）头部标记行——**这些转移点必须
  重置「当前组件」上下文**；转移后出现的属性行 → 报「组件块之外」（不允许归属旧组件）。
- 属性行缩进无含义（忽略），块归属由状态机确定（Header → Object → Component → Relations 阶段）。

### 3.5 属性行（值编码 = 自描述字面量 + token 系统）

```text
Max = 50                # int
Ratio = 0.5             # 浮点（含小数点/指数）
Alive = true            # bool
Name = "攻速"            # string（双引号 + 转义）
Kind = Huge             # enum 名（裸词）
Empty = null            # null
```

| token 类 | 字面量形态 | 说明 |
|---|---|---|
| Null | `null` | 唯一 null 字面量 |
| Bool | `true` / `false` | 大小写敏感 |
| Int | 整数（可选 `-` 前缀，纯数字） | 与浮点靠「是否含小数点/指数」区分 |
| Float | 含 `.` 或 `e/E` 的十进制 | double 语义由目标 Schema 决定；序列化保证字面量可识别为浮点（如 `3.0`、`1e-5`） |
| String | `"..."` | 转义仅限 `\"` `\\` `\n` `\r` `\t`；**未知转义（`\q`）、悬空反斜杠、未转义内部引号、闭合引号后多余字符 → 语法错误（评审修订：严格转义）** |
| Bare | 裸词（非上述形态） | enum 名；或数值字符串（见 enum 冲突策略） |

- **非有限浮点（评审修订：拒绝策略）**：`NaN` / `±Infinity` 无合法字面量——`Serialize` 遇到非有限
  `float/double` 属性值 → 抛错（带组件/属性上下文）；`Deserialize` 不识别 `NaN`/`Infinity` 形态。
  `±0.0`、subnormal、最大/最小有限值、指数形态均为合法（round-trip 保真）。
- **enum 冲突策略（评审修订）**：enum 名若命中保留 token（`null`/`true`/`false`）或可解析为数字
  （如 `@true` 转义关键字、未命名组合值）→ `Serialize` 输出**底层数值字符串**（如 `0`、`18446744073709551615`），
  Deserialize 按 Int/Bare token，Restore 对 enum 目标用 `Enum.ToObject`/`Enum.Parse` 兜底（R26）。
- **转换矩阵（评审修订，Restore 层）**：目标属性类型与 token 严格匹配——
  `int` 只收 Int；`string` 只收 String；`bool` 只收 Bool；`enum` 收 Bare/Int/Float（数值）/
  String（`Enum.Parse`，名字或数值字符串）；`float`/`double` 收 Int/Float（Invariant 转换，
  超范围/溢出 → 报错）；`null` 只允许目标为引用类型/可空（非 nullable 值类型 → 报错）。
  转换错误统一包装：对象索引 + 对象名 + 组件类型 + 属性名 + 目标类型 + 原字面量（评审修订，
  替代无边界 `Convert.*` 的静默舍入/漂移）。
- 属性名 = Schema 声明属性名（`[GameProperty]`，稳定）；缺失属性由 R24 策略（Throw/Skip）处理。
- **重复属性名（评审修订）**：同一组件块内属性名重复 → `Deserialize` 报错（防覆盖语义歧义）。
- 布尔/数字用 InvariantCulture；字符串全链路 UTF-8（fork 中文化基线）。
- 属性行顺序 = Schema `SerializedProperties` 声明序（确定性；跨构建稳定性依赖 R22 委托与声明序，
  O4 如需跨重排稳定应引入显式 Order——见 §6.4）。

### 3.6 关系行（序号引用）

```text
relation MyGame.TargetRelation #1 -> #2
```

- `relation <稳定全限定名> #<源序号> -> #<目标序号>`；序号语义见 3.3。
- 序号越界 → 解析报错；**类型未注册 → 由 Restore 层策略处理（评审修订：见 §5.1 UnknownRelationPolicy）**。
- **关系阶段（评审修订）**：v1 建议所有 `relation` 行位于全部对象之后（分区明确、状态机简单、
  可读性一致）；解析器同时允许先行出现（端点在行处已存在即可），但**不允许出现在对象之前**
  （端点为 0 个 → 越界报错）。

### 3.7 完整示例（评审修订：与语法严格一致，作为 golden test）

```text
format = "baize.object-components.v1"
kind = "scene"

# 商场关卡
object #0 "主场景"
object #1 "CubeA" parent = #0
[component MyGame.Health]
    Max = 50
    Current = 37
[component MyGame.Buff]
    Name = "攻速"
    Amount = 0.5
object #2 "敌人"
[component MyGame.Health enabled = false]
    Max = 100
    Current = 100
# 重名合法：两个 "哨兵" 靠序号区分
object #3 "哨兵"
object #4 "哨兵" parent = #3
relation MyGame.TargetRelation #1 -> #2
```

## 4. 确定性保证

- **顺序**：对象 = DFS 序（连续 + 前序双重校验）；组件 = 插入序；属性 = Schema 声明序；关系 = 插入序。
  三者都是系统既有确定性（Capture/ComputeHash 同口径）。
- **值**：数字用 InvariantCulture；float/double 规范化（保证可识别为浮点）；string 严格转义规范；
  enum 名或底层数值（位模式语义与 R9 hash 一致）。
- **引用**：`#n` = 快照索引直译，无名字查找、无歧义；序号连续 + DFS 前序 + 引用越界/自引用三重校验。
- **同一快照 Serialize 两次 → 字节相等**（可 diff 前提）；`Serialize→Deserialize→Serialize` 幂等。
- **编码规范（评审修订，§6.4 明细）**：Serialize 固定 LF 行尾；Deserialize 接受 LF/CRLF；末尾无换行合法；
  UTF-8 无 BOM 写入、容忍 BOM 读取；非配对 surrogate / Unicode normalization 保持原样不转换。

## 5. 与容错层的衔接

### 5.1 未知组件/未知属性/未知关系（评审修订：R24 扩展）

- `Deserialize` 只做语法 → 快照；**语义容错在 `Restore` 层**（`RestoreOptions`）：
  - 语法错（版本不匹配、缺头部、头部重复/乱序、序号不连续、DFS 前序违规、引用越界或自引用、
    属性在组件块外、重复属性名、非法转义、块头尾垃圾）→ `Deserialize` 抛错（带行号）；
  - 语义未知（未注册组件类型、未知属性名）→ `Restore` 按 `Throw`/`Skip` 处理（带对象/组件/属性上下文）；
- **UnknownRelationPolicy（评审修订）**：草案 v1 明确**未知关系类型恒为错误**（`RestoreTyped` 未注册即抛，
  带关系类型与源/目标序号上下文）；未来如需宽容加载，再在 `RestoreOptions` 增加
  `UnknownRelationPolicy`（与组件/属性并列）——本阶段不引入假实现的策略。

### 5.2 编辑器保存保真（评审修订：运行时快照 vs 文档模型）

**R24 Skip 是有损实例化，不适合 O7 编辑器 round-trip**：
- 运行时宽容加载（插件缺装时跳过未知组件继续跑）→ 用 Restore + Skip，可接受有损；
- **编辑器加载-保存必须保真**：缺少插件时加载场景、用户只改局部、保存——未知组件/属性/关系
  不得从文件中消失。O4/O7 引入**独立 authoring document model**（保留未知组件原始块、未知属性
  token/原文、未知关系、未来元数据、源顺序），编辑器保存从 document model 重写而非
  Restore→Capture 重建（见 §6.3）。本层 `Serialize/Deserialize` 只服务运行时快照，不承诺文档保真。

## 6. O4 落地指引（本草案的消费方；评审修订扩充）

### 6.1 静态格式与文件层

- `.bscene` 文件 = 本文档 `kind = "scene"` 编码 + 文件级元数据（O4 定：Resource references 表、
  scene settings、B3 override 记录）。
- `.bprefab` 文件 = `kind = "prefab"` 编码（O4 定：单 root、可嵌套 Prefab、无关卡全局状态——方案 §6.2）。
- Loader（O4）复用 `Deserialize` 得到快照 → `Restore` 建世界；编辑器（O7）落盘复用 `Serialize`
  （运行时路径）；文档保真路径走 §6.3 document model。

### 6.2 AuthoringId 双身份（评审修订：与 #序号正交且互补）

- 本层 `#DFS序号` 是单次快照的**临时拓扑索引**；O4 的持久作者身份 = **AuthoringId**：
  - 文件内：`object @<AuthoringId> "<名字>"`，`parent = @<父ID>`，`relation … @src -> @dst`；
  - loader：先建 `@ID → #DFS索引` 映射，再生成快照（复用本层序号契约，不推翻）；
  - 用途：重排/重命名的稳定参照、prefab override 定位（**override 绝不能用 #n 定位**，
    必须 `AuthoringId + ComponentStableType + PropertyPath`）、多人 Git 合并、跨场景引用。
- `GameObject.AuthoringId`（契约 §8 预留）、`SourceTemplate`（prefab 引用）为**对象级**字段，
  O4 在 document model 中落地；不能只靠文件头一条 metadata。
- 身份口径统一：`Identity.cs` 对 AuthoringId 的「参与确定性序列化」注释需在 O4 修订为
  「文档模型身份，不进入运行时快照 hash」。

### 6.3 文档模型与未知数据保留（评审修订）

- O4 定义 authoring document model：
  - 保留未知组件的原始块、未知属性的 token 值/原文、未知关系、未识别未来元数据、源顺序/位置；
  - 运行时快照（本层）只承载已知 Schema 数据；投影方向 document model → snapshot → world 单向；
  - 编辑器保存 = document model 重写（已知部分经 Schema 规范化，未知部分原样回写）。

### 6.4 编码与迁移明细（评审修订）

- **资源引用**：Primitive 白名单不含引用类型。O4 需要属性级引用 token 语法
  （如 `Mesh = resource("res://models/a.mesh")`、`Template = prefab("guid:…")`、`Target = object(@…)`）
  与文件级依赖表并存；定义规范化路径/GUID、null 与缺资源、外部/内嵌资源、依赖表排序、
  hash 是否含路径等内容——本层不臆造字段。
- **Schema 迁移版本**：组件数据需要 `SchemaRevision` + type/property alias + old→current 纯数据迁移；
  **不序列化 `GameComponent.Revision`**（那是运行时 tick 重挂版本，非作者数据）。
- **解析性能限额**：O4 loader 用 `TextReader`/span 逐行（替代 `text.Split('\n')` 一次性分配），
  定义最大文件/行/对象/组件/属性/关系/层级/字符串长度；超限报确定性错误而非 OOM。
- **属性声明序稳定性**：反射 `GetProperties` 顺序不保证跨构建稳定；O4 编辑器持久层应引入显式
  属性 `Order` 或稳定字段 id 排序（本层 Schema 声明序仅保证本次进程内一致性）。
