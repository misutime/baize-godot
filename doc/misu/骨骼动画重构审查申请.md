## 首要任务是判断方案是否适合需求

请先独立判断，围绕用户的实际目标，整个功能的设计思路、实现逻辑和实现方式是否合适。功能说明描述当前实现，审查需要回到需求判断它是否值得采用。现有资源划分、关联方式、保存规则和界面组织都可以重新评估。

需求适配、功能易用性和操作方便性与代码正确性具有同等审查地位。请检查新用户能否迅速理解概念，常用任务能否直接完成，操作入口是否容易发现，配置和保存步骤是否必要，执行结果是否符合用户预期。代码按当前设计正确运行时，设计本身仍可能存在不合理、不完整或不方便之处，这些问题同样需要明确报告。

请把主要需求映射到实际使用路径，指出完成任务需要打开哪些资产、设置哪些关系、经过哪些操作、保存哪些对象，以及用户需要掌握哪些隐含前提。以导入同骨骼动画、让多个模型直接使用、打开片段预览和修改当前片段为例，判断现有流程是否足够直接，是否存在可以省去的手动绑定、重复配置或保存步骤。

架构审查也需要判断采用当前实现方式的合理性，例如把目录放在骨骼里、用场景表示 SKMesh、同时支持内嵌与共享图、复用原生编辑器及统一文档生命周期，是否有清楚的收益与职责边界。请结合具体需求给出更简单或更合适的替代方案，必要时可以推翻现有结构。建议应同时展示调整后的用户操作流程及实现影响。

最终结论需要回答“这套方案是否满足需求、是否容易理解、是否方便使用、设计和实现方式是否合理”，并给出功能与流程方面的具体改进。代码缺陷列表和测试通过结果只是整体判断的一部分依据。

## 产品背景和取舍

主要面向以后用定制引擎创建的新 3D 项目，目前没有已上线产品依赖本轮自定义资产格式。用户更重视职责清楚、操作直接、流程少、文本可读和 AI 可读写。自定义原型的历史兼容不应成为持续增加复杂度的理由。

核心期望是导入时建立骨骼、模型和动画关系。相同骨骼的多个模型自动获得新导入动画；从文件系统直接打开骨骼或片段可以预览；片段常用修改覆盖保存到当前资产；动画组合在独立的图文档中编辑。

模型更新采用当次选择文件，只更新指定 SKMesh。骨骼保持明确身份，更新模型不自动改骨骼；动画再次导入作为新片段。没有长期源文件身份、自动重新导入及动画修改合并的需求。不要为了恢复早期原型的这些行为增加机制。

当前先支持同骨骼动画，不做自动重定向。用户过去表达过“不匹配给提示”的需求，最终实现采用骨名、层级与 Rest 全部匹配才允许导入。请评估这个严格程度是否与日常同骨骼工作流相符，是否会把可以直接使用的动画拦在门外，并明确其对“同骨骼”的产品定义。

原生引擎既有资源、第三方插件和通用编辑器行为仍需评估。对本轮旧原型不承担历史迁移负担，与对原生能力的回归责任需要分别判断。

## 功能设计与职责审查

### 资产关系是否能够直接理解

请从第一次接触系统的开发者视角，核实 `.sk`、`.skmesh`、`.anim`、共享目录、AnimationPlayer 和 AnimationTree 的关系是否容易解释。用户是否需要知道多个隐藏对象、额外约定或保存阶段才能完成常见操作？同一信息是否被多处保存并存在不同步的可能？

重点检查以下语义。

- 骨骼资产拥有定义和共享目录，片段独立，模型提供蒙皮与节点结构。AnimationPlayer 使用目录后，用户是否仍会误以为需要逐模型维护动画库？
- 骨骼“身份相同”与“结构兼容”是否区分清楚？复制、移动、重命名骨骼资产后，绑定和预览是否仍能解释？
- 一个骨骼关联多个模型时，默认预览模型选择、覆盖和丢失后的操作是否完整？打开动画能够找到模型的条件是否足够明确？
- 骨骼目录与片段的软硬引用、UID 和备用路径是否有必要且一致？编辑文本后是否会形成加载环或无法发现的孤立资产？
- `.skmesh` 作为文本 PackedScene 是否能像普通场景实例化、添加附件、保存配置，并在模型更新后保留这些工作？
- 新的 `.sk` 目录约束是否只作用于相关资产？对没有绑定骨骼的普通 AnimationPlayer，是否仍有清楚、可用的编辑路径？

请提出更简单的资产划分方案时，同时展示模型导入、追加动画、修改当前片段和共享动画图四条流程。抽象层数、配置项或文件数量的减少应能体现在这些操作里。

### 导入和更新是否完整

实际检查拖入 GLB、取消、多个输入、选择已有骨骼、创建骨骼、仅动画、无骨骼、同名资产及更新指定 SKMesh。重点评估常用入口是否可发现、错误是否明确指向原因、失败后用户能否直接重试。

检查骨骼名称、父子关系、Rest、索引顺序、导入根变换、单位与缩放对匹配的影响。相同骨架的不同网格或动画文件，是否会因源文件组织不同而无法使用？多个骨骼的 GLB 是否有完整的 UI 路径，还是仅存在内部导入参数？不能以底层支持推定用户入口已经支持。

检查标准化轨道是否保留需要的骨骼、根节点变换和 Blend Shape；哪些轨道被移除，是否会出现“成功导入但丢失必要动画”的情况？共享骨骼下不同模型的 Mesh 命名、Blend Shape 名称是否真的兼容？根移动和根旋转在导入、预览、剪辑、AnimationTree 使用之间是否一致、有设置入口且能解释。

模型更新要验证网格、Skin、材质、骨骼索引和绑定路径的实际结果，同时检查原场景中用户添加的插槽、脚本、节点引用及 AnimationTree 设置。更新失败、多资产导入中途失败、目标文件写入失败后的文件与缓存状态，属于有现实触发条件的一致性问题。

请区分必要的失败处理和过度防御。文件保存失败应能报告并保留用户编辑；为假设性跨进程事务建立通用框架则需要证明收益。当前逐资产写入是否需要局部回滚，应根据真实可能留下的半成品和重试行为判断。

### 片段预览和编辑是否方便

请实际完成“打开骨骼，搜索待机，切换跑步，暂停，拖到某帧，删除一段，再删除一段，撤销，重做，保存”流程。记录难以发现、步骤多或会误解的地方，并检查用户能否明确判断当前编辑的是哪个文件。

重点审查默认选择、默认循环、空格焦点规则、时间轴播放头与选区的区别、帧／秒切换、区间边界和整段删除限制。导入采样 FPS、源关键帧时间、Animation.step 与预览运行 FPS 是否被混为一谈？最后一帧、总帧数和片段结束时间是否有统一定义？

连续剪辑需要检查首段、中段、尾段、非整数时长、30／60 FPS 及连续撤销后的分支编辑。删除边界插值、旋转四元数、循环接缝、轨道属性、禁用轨道及动画标记是否被正确处理。请特别核实 markers、区段和未支持轨道的结果，现有文档没有把这些都声明为已完整支持。

确认“保存当前片段”确实更新使用中的同一资产，源对象身份、缓存和各引用者不会停留在旧内容。保存后撤销、撤销后再编辑、另存、切换资源、外部文本修改及保存失败都应有明确状态。

当前实现保留了普通或内嵌 Animation 的部分处理分支。请核实它们的实际保存目标，避免把“内嵌于动画库”误写为“属于场景”。有分支却不能完成一致操作时，可以完善或缩小入口，并清楚说明边界。

### 动画图的使用与共享是否清楚

核实默认内嵌 BlendTree、共享 `.animtree` 和转回内嵌副本的操作是否直观。绑定行为即时保存所属场景，图内容又可能单独保存，用户能否清楚区分？在修改绑定前，是否可能顺带保存用户尚不打算落盘的其他场景修改？

共享图工作副本、保存后的源资源、实际场景节点和编辑上下文需要有明确的所有权。多个 AnimationTree 共用图时，要验证结构更新和各自运行参数、状态机状态、播放进度的隔离。两个节点打开同一个文件时，检查器上下文是否会悄然切到另一个节点，用户是否能识别。

图内子节点属性、节点属性和图属性的入口需要稳定，Active、Root Motion、Tree Root 和 Anim Player 始终应可访问。无骨骼上下文、空 Output、无效连接和节点删除后的界面提示是否合理？原生图校验内容不能残留在关闭后的其他文档上。

## 文档标签和编辑器架构审查

这次标签机制以后还会承载更多编辑器内容。请检查它是否已经形成清楚的通用文档契约，场景、资源和唯一脚本容器各自的生命周期能否在同一个契约中表达。

重点检查打开、重复打开、激活、保存、另存、单独关闭、关闭其他、关闭右侧、关闭全部、取消关闭及编辑器退出。后台有修改的文档必须经过相同的保存判断；一个文档取消后，后续批量关闭应停止在清楚的位置。

检查固定标签、混排、拖动、快捷键、布局恢复、文件移动和所属场景关闭。场景树“在编辑器中打开”应激活目标场景，预加载根脚本不应抢占当前文档。动画节点双击名称或图标应使用同一规则，F2 和显式重命名入口继续有效。

架构上需要核实回调、ObjectID、资源引用、场景引用与撤销历史的归属。共享工作副本释放之前应解除检查器使用，延迟回调执行时目标必须仍存在。旧 EditorDock 被移入中央区域后，其停放、可见性、处理循环和销毁顺序是否清楚，是否依赖多处补偿性的 hide／focus／reparent 调用？

当前 `AnimationWorkbenchEditorPlugin` 同时包含导入窗口、预览、剪辑、保存和文档协调。请判断职责是否过于集中，哪些逻辑适合独立为可直接调用的操作，哪些保留在 UI 类中更简单。优先复用现有资源、导入器和撤销机制，提取以可验证的职责边界为依据。

## AI 开发和自动化验证专项

### 目标和当前事实

希望至少 90% 的维护性验收场景能够通过后台进程、命令、脚本或 MCP 完成，不抢用户输入焦点，不依赖逐步截图识别。前台电脑控制用于真实输入路由、视觉布局等需要验证的少数交互。

当前已具备脚本化导入／更新、骨骼比较、片段打开／删除／保存、图绑定和原生资源读写接口。多数本地用例使用 EditorScript 直接断言结果，部分交互通过 Viewport 输入事件合成完成；实际运行仍经常需要 GUI 启动脚本、切换焦点和读图。现阶段没有覆盖率统计，也没有验证所有编辑器接口都可在 headless 环境运行。

项目里的 `godot_ai` MCP 插件与这套引擎工具相互独立。审查不能默认新项目或 CI 已安装 MCP，也不能把有一个插件接口等同于存在可靠的后台测试入口。

### 建议评估的执行层次

| 层次 | 适合验证的内容 | 推荐方式与成功证据 |
| --- | --- | --- |
| 资源与数据 | 骨骼比较、资源格式、片段区间变换、序列化、软引用解析 | 原生测试或 headless GDScript，检查实际数据和冷加载结果 |
| 编辑器业务 | 导入、目录登记、模型更新、保存检查点、图绑定、文档生命周期 | 独立编辑器测试进程直接调用服务，返回结构化状态、文件及对象断言 |
| 渲染与预览 | 指定时刻骨骼姿态、Blend Shape、模型边界、预览相机和世界隔离 | 后台离屏渲染或独立非前台图形进程，以数值为主，必要时输出图像工件 |
| 原生输入与布局 | 双击／重命名、真实操作系统拖拽、空格焦点、遮挡和 DPI | 少量前台回归，明确前台操作覆盖的行为 |

合成事件可以在后台验证大量输入状态，但不能替代操作系统拖放和真实窗口焦点的最终集成验证。数值姿态断言也需要少量实际渲染检查，确认网格确实显示正确。

### 接口和执行入口需要审查的缺口

现有片段算法位于 UI 插件类，脚本取得插件对象还会依赖编辑器节点查找。请评估能否把删除区间等纯数据操作提取为直接可调用的小型服务，让界面、脚本和 MCP 共享实现。API 应能返回结果和错误原因，避免操作失败只能到界面 Label 里找文字。

导入服务已经提供 Dictionary 返回值，但内部仍复用编辑器导入链。请实测其在 headless 编辑器、独立测试进程中的初始化、文件系统扫描、进度窗口和异步完成行为。需要 UI 初始化的部分可以保留在适当执行层，核心资产处理不应仅能靠打开文件选择器触发。

文档操作宜提供稳定的状态查询和操作入口，覆盖打开文档、当前类型和路径、激活、dirty、保存、关闭结果、待确认原因及历史归属。播放、定位时间、循环和选区也应有可直接调用、可读回的入口。先核实现有接口，补齐实际用例缺口，避免仅为测试暴露全部私有状态。

MCP 如接入，应包装同一业务操作和结构化结果。它可以使用运行中的编辑器，也应允许在可控的独立测试进程中工作。验证正常业务时直接调用操作，少量输入测试才合成点击，避免所有步骤都绕回菜单和控件坐标。

建议采用一个简单、受控的测试启动方式，将项目路径、用例和输出目录作为参数，在空项目的编辑器生命周期准备完成后执行。输出应包含最终 head／构建标识、逐用例结果、结构化错误、日志、生成资产及退出码。不存在的命令或 MCP 方法必须标为建议，不能写成现有可执行入口。具体脚本、原生测试或编辑器启动钩子由实际依赖决定，无需先搭建通用远程执行框架。

### 可复现与 90% 的衡量

将实际验收场景列成固定清单，按资源数据、编辑器业务、渲染、前台交互划分。统计无需 foreground 激活、鼠标键盘接管或人工截图判断即可完成的场景数，占总维护性验收场景的比例。统计单位是有用户意义的验收场景，避免通过拆分大量简单断言提高比例。

后台用例成功应同时满足进程退出成功、断言完成和结果文件可读。无输出、未触发断言、运行到一半或只编译通过均不算通过。资源保存后应冷加载或在新进程读回，不能仅检查当前资源缓存。

测试资产需能在干净克隆中生成或随仓库分发，包含最小的双模型共享骨骼、不同骨骼和几段短动画。无需依赖开发机路径和商业素材。并行用例使用各自临时项目和输出目录，记录可重跑所需信息。

本地 `bin/misu` 被 Git 忽略，其中的历史测试脚本和日志可供本次本机审查直接查看和复用。长期维护仍需要明确适合纳入仓库的最小回归集与执行命令，清理重复或过时用例，并判断干净克隆能否复现必要验证。

请给出达到 90% 目标所需的最小改造方案，并报告实际验证比例。达不到时说明哪些场景仍需前台、原因和替代成本。本文没有预先宣称目标已经实现。
